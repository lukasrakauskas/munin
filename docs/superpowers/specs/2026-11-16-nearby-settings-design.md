# Nearby pairing, desktop settings and pairing effects

## Intent
Make two Munin devices on one local network easy to find and explicitly connect without sending invitation codes. Replace the mobile-like settings card feed with a desktop tabbed workspace, and celebrate completed pairing with rune-fx. Continue inline without questions/subagents, per the user's instructions.

## Approaches
Automatic LAN trust is rejected: sharing Wi-Fi does not authorize reading notes. Broadcasting invitation capabilities is rejected because every LAN participant could redeem them. Chosen: opt-in mDNS discovery publishes only a friendly device name, endpoint identity and direct IP addresses. A separate authenticated iroh pairing protocol exchanges bounded metadata, shows the same session verification fingerprint on both screens, and requires Accept on both before granting sync access. Existing invitations remain available for blocked multicast/different networks.

## Security / lifecycle
Nearby discovery is a non-persistent ten-minute window, only available when workspace sync is enabled. Stopping discovery, pausing sync, changing workspace or closing the app stops advertisement and cancels pending nearby requests. Peer discovery never grants trust. Names are untrusted; UI shows a 48-bit verification fingerprint derived from both authenticated endpoint IDs and fresh per-session nonces, in role-independent order, to compare on both devices. Each side commits to its endpoint-bound nonce before either reveals it, preventing adaptive short-fingerprint grinding. No document or invitation secret is sent on the separate pairing ALPN. Each request has a fresh 256-bit nonce, a 90-second deadline, endpoint-bound decision handle, explicit Accept/Decline, at most eight pending sessions, and no approval reuse. Simultaneous/repeated requests must not bypass consent. Existing trust uses the existing encrypted sync ALPN after both approvals. Names/direct addresses are LAN-visible only during discovery; no workspace names, contents, tokens or private keys are advertised. Expiry/removal events remove nearby candidates; stale UI decisions cannot authorize a later request. Show actionable multicast/firewall/failure guidance and invitation fallback.

## Settings design
Desktop header and native keyboard-accessible General / Sync / Privacy tabs. Default Sync preserves the existing settings entry's purpose. General has compact appearance rows; Privacy owns trust/storage/discovery explanations. Sync uses up to 1120px with a compact overview/identity column and a wider connection column; on smaller windows it stacks without horizontal overflow. The code viewport remains clipped with separate Copy/Revoke controls. Nearby devices and incoming/outgoing confirmation requests are prominent; device name, short key and matching verification fingerprint are shown. All note data and active editing focus stay intact across tab changes. Escape returns to notes; file/action palette continues to work.

## Success effect
A persistent, dismissible success banner names the newly paired device. Only the first successful document exchange of a newly authorized peer triggers its celebration, not an incoming request, partial grant, failed transfer, ordinary reconnect or every autosync. rune-fx supplies a short sparkle burst and glow/ripple around the success banner, driven by Rune animation time and a seed/sequence. Stop drawing after the one-shot ends; no idle animation. Reduced motion keeps the success message and a calm non-travelling effect. Render with a small compositor drawing the ordinary UI unchanged plus bounded layers, handling device/format changes.
